# AGENTS.md

## Project overview

Room Reservator is an interactive TypeScript CLI/TUI for FHNW students and staff. It signs in through the official `raum.fhnw.ch` browser flow, calls the FHNW Evento API, lists bookable rooms for a campus and time range, creates reservations, shows upcoming reservations, and cancels eligible reservations.

This is a small, early-stage project. The source of truth is the code in `src/`; the current README and package metadata contain some stale or incomplete setup details.

## Stack and runtime

- Node.js (use Node 18 or newer; the application relies on the built-in `fetch` API)
- TypeScript with strict mode, ES2022 target, and NodeNext module resolution
- `tsx` for development execution
- Playwright/Chromium for FHNW SSO login and API discovery
- `@inquirer/prompts` for interactive prompts
- `cli-table3` and `dayjs` for terminal output and date handling
- CommonJS package output (`package.json` has `"type": "commonjs"`), while relative TypeScript imports deliberately use `.js` extensions for NodeNext compatibility

## Repository map

- `src/index.ts`: CLI entry point and orchestration. Owns the main menu, reserve flow, cancellation flow, and one-time retry after a `401`.
- `src/auth.ts`: Playwright-based SSO login, session/token caching, and API header construction.
- `src/api.ts`: FHNW Evento API client. Fetches buildings and available rooms, creates/deletes reservations, and fetches the current user's reservations.
- `src/ui.ts`: All prompts, input parsing, confirmation screens, and terminal tables.
- `src/locations.ts`: Hard-coded supported FHNW campuses and Evento site/building IDs.
- `src/types.ts`: Interfaces for API payloads and local auth/site state. API field names intentionally retain their PascalCase spelling.
- `src/sniff.ts`: Developer-only Playwright utility that records Evento API requests/responses while the web app is used.
- `dist/`: Generated by TypeScript and ignored by git.

There is currently no automated test suite.

## Setup and common commands

```sh
npm install
npx playwright install chromium
npm start
```

Useful package scripts:

- `npm start`: run the interactive CLI from TypeScript.
- `npm run login`: force an interactive browser login and refresh saved authentication.
- `npm run dev`: run the CLI through `tsx watch`.
- `npm run build`: type-check and compile `src/` into `dist/`.
- `npm run sniff`: open the FHNW room web app and capture its Evento API traffic for endpoint investigation.

After changing code, at minimum run `npm run build`. Exercise pure display/input logic manually when relevant. Do not use live reservation or cancellation requests as casual smoke tests: they modify real FHNW data.

Known packaging gaps:

- `package.json` declares `bin/roomreserve.js`, but that file is not present.
- `README.md` mentions `setup.bat`, but that file is not present.
- The `discover` script passes `--discover` to `src/index.ts`, but the argument is currently ignored. Use `npm run sniff` for API discovery.

## Application flow

1. `index.ts` calls `authenticate()` before showing the main menu.
2. `auth.ts` uses an unexpired cached API token when possible. Otherwise it launches Chromium, visits `https://raum.fhnw.ch`, waits for a request to `eviapi.fhnw.ch`, and captures the `clx-authorization` header.
3. The reserve flow prompts for campus, local date/start time, and duration. It queries available rooms by Unix timestamps, filters for `IsBookable && IsAvailable`, asks for reservation details, then sends ISO timestamps in a reservation POST.
4. The reservations flow derives `id_person` from the JWT embedded in the authorization header, fetches upcoming reservations, and allows deletion only when `IsCancelable` is true.
5. API calls that return `401` throw the sentinel error `AUTH_EXPIRED`. `withAuth()` forces a new interactive login and retries that operation once.

## External API assumptions

- Base URL: `https://eviapi.fhnw.ch/Evento/api2`
- Web app/referer: `https://raum.fhnw.ch/`
- Authentication is forwarded in the nonstandard `clx-authorization` header captured from the web app.
- Availability uses epoch seconds in query parameters; reservation creation uses JavaScript `Date.toISOString()` values.
- `POST /Reservations/` may return `201` with an empty body and a `Location` header. The client follows that location when available, otherwise it returns a minimal synthetic success object.
- Campus IDs in `src/locations.ts` and response shapes in `src/types.ts` are reverse-engineered external contracts and may change independently of this repository.

Keep all network behavior in `src/api.ts`, browser/session behavior in `src/auth.ts`, interaction/rendering in `src/ui.ts`, and orchestration in `src/index.ts`. If the API contract changes, update the relevant types and call sites together.

## Authentication, privacy, and safety

Runtime data is stored outside the repository under `%APPDATA%/roomreservator` on Windows or `$HOME/.config/roomreservator` elsewhere:

- `auth.json`: captured authorization header and expiry
- `browser-session.json`: Playwright browser storage/cookies
- `api-log.json`: sniffer output, including request headers, bodies, and responses

Treat all three as secrets. Never commit, print, paste into issues, or use as fixtures without thorough redaction. In particular, sniffer output can contain live tokens and personal/reservation data. Do not weaken `.gitignore` protections for secrets, and do not add hard-coded FHNW credentials or tokens.

Reservation creation and cancellation target the live FHNW service. Preserve confirmation prompts around mutations. Mock `fetch` and authentication for future automated tests; never require an FHNW account or live API access in unit tests.

## Implementation conventions and pitfalls

- Preserve the `.js` suffix on relative imports in `.ts` files; this is required by the configured NodeNext resolution/output model.
- Keep TypeScript strict and avoid spreading `any`; the sniffer is currently the main exception because it handles exploratory payloads.
- Maintain the API's exact PascalCase field names at the transport boundary. Introduce explicit mapping if a camelCase application model is desired.
- Date prompts are interpreted in the machine's local timezone, while `toISOString()` serializes UTC. Test date changes around midnight and daylight-saving transitions when editing time logic.
- Date validation currently checks shape and whether JavaScript can construct a date; JavaScript normalizes some impossible calendar dates. Be deliberate if tightening this behavior.
- The duration validation message says `0–16 hours`, but zero is rejected; preserve the actual rule (`> 0 && <= 16`) or update both together.
- `buildingIds` and `fetchBuildings()` are not currently used by the main flow. Do not remove them without checking whether they support planned discovery work.
- Authentication retry depends on the exact `AUTH_EXPIRED` message. If error handling is refactored, replace this string protocol consistently (preferably with a typed error).
- User prompt cancellation is recognized in `index.ts` by matching Inquirer error messages. Verify Ctrl+C behavior when changing prompt libraries or error handling.

## Guidance for changes

- Favor small modules and preserve the current separation between UI, API, auth, and orchestration.
- For new API operations, route requests through `apiFetch()` so headers and `401` behavior remain consistent.
- Validate response failures before parsing JSON and include HTTP status/context in user-facing errors without exposing auth headers.
- Keep destructive operations explicit and confirmed by the user.
- Add tests around pure parsing/filtering/mapping code when extracting it from interactive flows. Useful first targets are date parsing, availability filtering, JWT person-ID extraction, and reservation rendering.
- If adding a distributable CLI, create and test the declared `bin/roomreserve.js` launcher and align the README, package scripts, and installation instructions in the same change.

## Commit messages

Use Conventional Commits:

```text
<type>(<optional scope>): <summary>

<optional short body explaining what changed and why>
```

- The first line (summary) must be lowercase, imperative, and at most 50 characters.
- Use a blank line before a body.
- Add a short body for non-trivial changes, explaining what changed and why.
- Prefer `feat`, `fix`, `refactor`, `test`, `docs`, `build`, or `chore`.
- Use scopes only when useful, for example `ui`, `api`, or `auth`.
